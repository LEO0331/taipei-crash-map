# 臺北公車路網與服務決策支援 MVP

Policy #5，方法 `bus-network-service-evidence-review-v1`。本版為公布路網與服務文件的研究 POC；實際營運歷史未通過資格，不發布服務可靠度或短缺排名。精確版本、數量與驗證見[交付報告](bus-service-delivery.md)，來源契約見[稽核](bus-service-source-audit.md)及[方法論](bus-service-methodology.md)。

## 1. 政策問題

交通主管機關若只能調查少數公車服務，哪些主路線、支線、方向、站序或公布服務文件值得優先確認？每個調查名額對應一個可解釋的證據問題，不代表乘客傷害或改善成效。

## 2. 研究範圍

以臺北公運處官方發布系統為來源範圍；資料包含跨市路線與站牌，不等於每筆都位於臺北市界。沒有官方相容行政區對照，不能宣稱行政區均衡、人口涵蓋或服務公平。本模組與事故、內湖交通模組獨立，不修改 Portfolio。

## 3. 官方資料

使用官方 v6.3 規格與 production `GetRoute`、`GetStop`、`GetStopLocation`、`GetPathDetail`、`GetSemiTimeTable`、`GetTimeTable`、`GetBusShape`、`GetSpecTimeTable` 壓縮檔。資料分別描述路線、站牌、實體位置、支線站序、公布班距、發車時刻、線形與預排班表；都不是完整的實際已執行班次。

## 4. 來源稽核

先檢查官方端點、HTTP、gzip、UTF-8、結構、紀錄數、SHA256、取得時間與來源更新字串，再建構分析。目錄的小型 CSV 是介接資訊；`Tst` 名稱的資源需要額外確認，不能因能下載就視為完整 production。舊 SHP 不能代替目前路網。TDX 文件、供應矩陣及新服務公告的查核另列於[存取補充](bus-service-access-notes.md)。

## 5. 實體與路線識別

保留來源命名空間、主路線 Id、支線 pathAttributeId、業者及方向。顯示名稱不是關聯鍵。官方 Route 同一主路線可有多支線，同一支線可有多個業者關聯；不能直接以重複 Id 刪除這些資料。

Stop.routeId 是主路線 Id；PathDetail.pathAttributeId 是支線識別，stopId 是站牌 Id。StopLocation 是實體位置，不是站牌、站名或站序。環線重複停靠以站次保留，不因站名或站牌相同去重。

## 6. 空間定義

地圖只顯示已驗證關聯及有效座標的所選路線站次，限制同時顯示數量。站點不連成虛構路線；主路線線形不能套到每個支線。未確認支線、方向或新鮮度的線形保持稽核資料，不冒充權威地圖。

本版不計算人口百分比、步行可達範圍、步行網路距離或需求。直線距離即使未來加入，也只能標為幾何近鄰假設。

## 7. 公布服務語義

路線首末班、公布班距、發車時刻、預排班表、GPS、預估到站與實際到離站是不同證據。像 `0510` 或自然語言的班距字串先保留，不直接轉成 510 分鐘。SemiTimeTable 的 LongHeadway／LowHeadway 可能出現順序不一致，不能任意交換而隱藏問題。

公布時刻須保留 DateType／DateValue、原始時間與解析結果。跨午夜以服務日偏移表示；特殊日及假日不可由週幾猜測。沒有方向欄位的支線班表只在支線層次展示，不複製到去返程。發車班距不是下游乘客等待時間。

## 8. 歷史證據資格

Mode B 須有實際到離站事件、明確時區及服務日、穩定主支線／方向／站牌對照、比較窗口、重複處理、完整率分母、例外及斷訊規則。GPS 或到站預估不能直接視為實際完成班次，缺 GPS 也不能認定脫班。

本次未取得可接受的官方實際歷史族群，因此 Mode B 停用並顯示原因。TDX 有歷史服務類別不等於已取得臺北完整已執行行程。2026-10-16 新增公車服務公告也不能自動作為每日班次歷史的證據。

## 9. 候選母體

預設候選為來源＋主路線＋支線＋可確認方向的資料查核單位。當服務窗口不能明確對應方向時，不增加假想時段候選。每筆保留穩定 ID、來源、方向或 unknown、問題、證據狀態、限制與未知指標。

資料品質、公布服務與實際歷史資格分開。納入模糊項目的敏感度只擴大待查清單，不把模糊對應變成已驗證觀測。來源導出的實際候選數與排除數載於交付報告，不能用 fixture 的數量代替。

## 10. 調查優先順序

A：來源、識別或站序關係需要首要確認。B：公布服務文件缺漏、衝突、方向或日期不明。C：其他較低優先的文件／幾何查核。這些是調查分級，不是公車品質等級。

排序使用明確問題類別與穩定識別碼；不以任意權重計算短缺分數。相同分級的候選若沒有其他受支持的差異，應說明排序只是固定的查核順序。

## 11. 容量策略

提供 5、10 與全部合格候選。證據缺口優先依已定義規則選取；路網平衡在已確認的不同主路線間輪流分配名額。沒有行政區對應時，只呈現主路線／支線多樣性，不承諾地理公平。

輸出符合、排除與入選候選、實際使用名額、代表路線與支線數、理由及限制。兩種策略若產生相同清單如實呈現，不能刻意製造策略差異。

## 12. 敏感度假設

保守設定預設排除不明識別；較廣設定可將模糊對應納入品質查核。比較容量與策略時固定來源版本、候選識別及資格。若來源、解析／模糊納入條件或候選母體改變，標示不同證據範圍。

不提供沒有資料支持的半徑、人口或政策權重控制。較寬鬆的設定不允許通過實際歷史資格，也不產生假想服務改善百分比。

## 13. 實際來源結果

保留的 production 來源有 800 筆 Route 資料、416 個主路線 Id、731 個支線 Id；28,826 筆站牌、5,376 個實體位置、43,447 筆路徑站次。路線資料含 773 個不同的主路線／支線／業者組合：42 個額外業者關聯與 27 筆完全相同組合的重複列，不能全部混稱為業者差異。PathDetail 有 212 筆支線參照無法在 Route 解析，須保留異常而非默默丟棄。

這是來源清冊數，不是運行班次或需求。最終保留版本及正規化後的有效／排除數、5／10 名額實例以交付報告與來源雜湊為準；不同擷取版本不可混成同一快照。

## 14. 排除與限制

未解析關聯、缺座標、缺方向、站序不完整、班表日期衝突與過時線形都以問題呈現；缺資料不代表零服務。無法驗證的跨來源 ID 不強行對接。異常站牌仍可在來源稽核追溯，不能以附近名稱補出關係。

不推論乘客需求、服務不足、實際頻率、可靠度、公平、路線重疊效率、事故因果、改善效益或路線撤併必要性。

## 15. 使用互動

開啟「公車路網與服務」，先看來源／歷史資格，再選主路線、支線或方向，檢查站序與公布服務文件。選查核目標、名額與策略，對照敏感度，最後匯出摘要。

中文預設，可切英文。載入、空資料、無效快照與重試狀態明確。JSON／CSV 保留真實選取 ID、快照、來源雜湊、資格與限制；CSV 防試算表公式注入。

## 16. 系統架構與效能

明確離線擷取 → 有界解壓與結構驗證 → ID／站序對照 → 品質與服務文件稽核 → 版本化靜態索引／路線詳情 → 延遲載入介面與情境 → 摘要匯出。

大量關聯離線完成；瀏覽器只在進入分頁後取索引、選路線後取詳情並快取，不同時畫全市數千點。既有 appUrl 支援 Pages 基底路徑；不增加大型 PWA 預快取。實際壓縮檔、JSON、chunk 與運算時間列於交付報告，不以本機數值保證公網延遲。

## 17. 測試與可重現性

執行公車 fetch／audit／build、相同保留輸入重建比對、來源與識別測試、時間與班表測試、情境／匯出測試、雙語與載入整合測試、一般／Pages 建置及桌面手機瀏覽器檢查。

原始 gzip 位元組與 SHA256 保留，離線重建沿用來源取得時間。暫存完整版本驗證後才發布 manifest，失敗保留上一版。憑證不進入 Git、VITE 變數或公開 JSON。沒有實際歷史時的測試資料明示合成，永不進入 production。詳細命令、結果與未測項目見交付報告。

## 18. 後續擴充

先確認異常支線對照、日期與方向適用性、線形更新及官方市界資料，再評估擴充公布服務查核。歷史分析另需有權限且可重現的實際事件、完整率分母、服務日／假日與路線變更記錄；須重新稽核 TDX 當期契約與配額。

未來 Portfolio Case Study 007 可引用本模組的來源整合、識別規則、可重現 ETL、證據限制與實際查核案例。本次不修改 Portfolio，也不把清冊 POC 宣稱為全面驗證的服務涵蓋或營運績效研究。
